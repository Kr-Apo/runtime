# T840B2 — Production clock contract

Status: core scheduling API only. No current viewport, evaluator, PhysicsState,
RigPlayer, PixiJS or Phaser path uses it. ReplayV1 simulation is not implemented.

## Representation and activation

Rust module: `ankhimate_core::replay_clock`. TypeScript: public core entry point
exports `ReplayClock`, `ClockError`, `SimulationProfile`, constants and types.
`SimulationProfile` distinguishes `LegacyT839` from `ReplayV1`; Rust's enum
defaults to LegacyT839. Constructing a standalone ReplayClock explicitly selects
the future clock semantics; it does not switch any existing player profile.
The existing default consumers are unchanged. No profile is persisted/exported.

Each clock owns its own epoch, last exact rational time, requested/completed tick
and initialization state. Snapshot derives backlog and next pending tick. It
holds no asset, constraint, velocity, anchor, clip or pose. Storage is O(1);
processing stores no tick list. Consumer work is synchronous.

Integers share the domain **0 through 18,446,744,073,709,551,615** (u64). Rust
accepts u64 inputs, with exact u128 multiplication/comparison. Negative or larger
integers cannot enter that typed API; callers must validate external conversions.
TypeScript requires `bigint`, checks the same domain, and rejects `number`,
negative values and oversized BigInts. No implicit numeric coercion is provided.

Tick N denotes **N/120 second**; the source of truth is N, never repeated f32
addition. `request_time(n,d)` computes `floor(n*120/d)` with checked bounds.
Both rational operands must fit u64; d must be nonzero; the resulting target
must fit u64. Fractions are reduced by GCD (zero becomes 0/1). Comparing reduced
times uses exact cross-products, each fitting u128, including near boundaries.
An equivalent rational is the same time even if its denominator differs.

## Public operations

| Rust / TypeScript | Semantics |
|---|---|
| `new()` / `new ReplayClock()` | Uninitialized; epoch 0, no implicit historical work |
| `reset(epoch)` | Nonzero epoch strictly greater than this clock's previous epoch; sets exact time 0/1 and counters/backlog to zero |
| `snapshot()` | Observation only, never advances or initializes |
| `request_tick(epoch,N,consume)` / `requestTick` | Exact absolute N/120 request; process at most 8 pending ticks if time increased |
| `request_time(epoch,n,d,consume)` / `requestTime` | Exact absolute rational request; same work budget |
| `pump(epoch,budget,consume)` | Explicit processing of already requested work; budget is an integer in 1..=65,536 |

Requests are absolute times in an epoch, not deltas. An exact backward time is
refused, including regression within one floor tick. An exactly equal request
returns `unchanged` without calling the consumer, draining backlog or changing
any clock state. Rational positive advancement within the same floor tick is a
new logical time and can process existing backlog. This distinction is explicit
and tested; callers wanting observation must call snapshot or repeat the exact
time, not construct a newer fraction.

One request belongs to one instance, not one constraint. Future integration
must evaluate a whole instance's tick before returning Complete. B2 does not
attach this clock to any constraint loop.

At a half-second hitch: target=60, eight successful consumer calls commit
ticks 1..8, backlog=52, next=9. Repeating 1/2 (or 2/4) performs no work. Pumping
with budget 7 commits at most ticks 9..15 and leaves backlog=45. Repeated pumps
can reach 60; no request silently discards debt. A later positive request can
extend the pending range before it has drained.

## Plan, begin, commit and interruption

The requested counter and snapshot `next` describe pending work. Calling the
consumer with `{epoch,index}` begins an attempt. Only `TickResult::Complete` /
`{kind:"complete"}` advances completed. The consumer must check cancellation
before performing its tick, returning Cancelled when interrupted between ticks.
Failed or Cancelled leaves that same index pending, with the completed prefix
retained. A pump can retry it. An unchanged request after failure cannot retry it.

Progress reports snapshot, successful `processed` count, `attempted` count and
stop reason: target reached, budget exhausted, unchanged, cancelled or failed.
Failed/Cancelled counts its offered tick as an attempt, not a completed tick.
A successful request is not a claim that its target has been reached: inspect
completed/backlog/stop. No simulation events are generated by this clock.

Rust uses a generic consumer error payload; TS uses an unknown payload. Normal
consumer failures are progress outcomes, distinct from invalid-input ClockError.
TS thrown callbacks become failed outcomes; a finally guard releases processing.
Rust panics unwind normally: completed still reflects only the successful prefix,
but callers should return Failed rather than panic. A test checks the counter
after caught unwind; no cross-language equivalence of exception mechanics is
claimed. Async TS callbacks are unsupported and treated as failed, not awaited.

Rust's mutable borrow prevents reentrant clock mutation. TS rejects reset,
request and pump while its callback runs (`busy`); snapshot remains readable and
shows the tick still uncommitted. This is not a concurrent worker/thread API.

**No consumer-state rollback:** failure may have changed the caller's data
before it reports failure. B2 guarantees only the clock commit boundary. B6 must
provide atomic recovery of physical offsets, velocities and anchors. Retrying a
partially applied consumer without caller rollback is not safe replay.

## Errors, epochs and limits

Validation occurs before clock mutation for invalid inputs: `uninitialized`,
`invalid_epoch`, `invalid_time`, `overflow`, `backward_time`, `invalid_budget`.
TS additionally reports `busy` because its borrow discipline is dynamic.
Zero denominator, rational-result overflow and invalid pump budgets cannot
change the requested/completed counters or exact time. Counters cannot wrap:
completed+1 is used only when completed < requested <= u64::MAX.

Epochs are scoped to a particular clock instance, not globally unique asset IDs.
Only that clock's current epoch can submit work; old epochs are rejected after
reset. At the largest epoch no further reset is possible; it is refused rather
than wrapping. Callers own context identity and must never route a token from
another clock merely because its numeric epoch matches. B3 must bind clock and
simulation state to their owning context, preserving B1 disposal semantics.

No seconds/delta bridge is shipped. Exact integer nanoseconds can be supplied
as n/1,000,000,000, within the same operand bounds. The T840A experiment's biased
`(ns*120+60)/1e9` boundary adjustment is not adopted: it differs from exact floor
for some nanoseconds just below a tick. Rounded nanoseconds cannot represent
every N/120 boundary exactly. Float rounding, drift, pause and wall-clock
conversion policies require separate qualification; rational conformance proves
none of the existing `deltaSeconds` paths.

No clock object is added to .ankh or runtime v1/v2. BigInts have no implicit JSON
encoding; the tests explicitly encode decimal strings for their isolated clock
vectors only. There is no restore-from-JSON or replay snapshot API.

## Minimal explicit use (future non-graphical consumer)

```typescript
const clock = new ReplayClock();
clock.reset(1n);
const first = clock.requestTime(1n, 1n, 2n, tick => {
  // Complete the caller-owned whole-instance work for tick.index first.
  return { kind: "complete" };
});
// first.state.completed === 8n; first.state.backlog === 52n
const rest = clock.pump(1n, 52, () => ({ kind: "complete" }));
// rest.state.completed === 60n
```

This illustrates scheduling, not a Physics implementation. No new adapter or
promise of visual/Rust-runtime simulation parity follows from it.
